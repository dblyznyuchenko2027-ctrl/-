# Висновки ПР7

## Стан виконання

Реалізовано конвеєр підготовки зображення → мультимодальна модель → JSON-схема → програмні правила → `auto/review/reject`, а також веб-обробку типових помилок.

### Що перевірено без API
- синтаксис модулів;
- відкриття/EXIF transpose/масштабування зображень;
- JSON Schema;
- IBAN ISO 13616 mod 97;
- контрольні розряди ЄДРПОУ та РНОКПП;
- арифметика з `Decimal`;
- правила покупця, довідника постачальників і дат;
- створено два власні тестові зразки, один із них є симуляцією фото телефоном.

### Що потребує запуску з ключем моделі

Повний прогін усіх 27 стандартних зразків + 2 власних вимагає `LLM_API_KEY`, оскільки саме модель має прочитати зображення. Щоб не вигадувати результати, фактичні точність, токени, час і кількість тихих помилок не заповнюються наперед.

Запуск:
```bash
python eval_runner.py
```

Результат: `eval/results.json`.

## Проєктні рішення

1. Зображення приводиться до правильної EXIF-орієнтації і зменшується до `IMAGE_MAX_SIDE=1600`; PNG використовується як формат без втрат для дрібного тексту.
2. Відсутнє або нечитабельне значення — `null`; модель не має права обчислювати відсутні підсумки або «виправляти» надруковані числа.
3. Гроші проходять арифметичні перевірки через `Decimal`, а не `float`; допуск — 1 копійка.
4. `auto` можливе лише для рахунку без помилок правил і без пропусків обов'язкових полів.
5. `review` використовується для проблем, які потребують людини; `reject` — для іншого типу документа або відсутності суттєвих даних.
6. Текст на зображенні не має окремого поля для зміни рішення: рішення приймає лише код за результатами правил.
7. Повні персональні реквізити не логуються.

## Відповіді на контрольні питання

1. Зображення передається як `data:image/png;base64,...` у `image_url`. Воно витрачає токени/ресурс моделі, тому більша роздільність дорожча. Базовий компроміс — 1600 px за довшою стороною; фактичну різницю з 800 px треба виміряти запуском `eval_runner.py`.
2. Мультимодальна модель бачить документ разом із просторовою структурою; OCR дає текст і координати, але структуру таблиці треба відновлювати окремо. OCR має власні сигнали впевненості, тоді як впевненість генеративної моделі не слід вважати надійним доказом.
3. Значення треба переписувати, а не виправляти: інакше помилка постачальника може тихо зникнути. `rahunok-05` спеціально призначений для перевірки цього; арифметичне правило має відправити документ на review, якщо надрукована сума не збігається з кількістю × ціна.
4. Для відсутнього/нечитабельного значення використовується `null`. На обрізаному зображенні підсумки не повинні відновлюватися з позицій.
5. IBAN перевіряється перестановкою перших чотирьох символів у кінець, перетворенням літер на числа A=10…Z=35 і `mod 97 == 1`. `rahunok-08` може мати правильний IBAN, але пройти його не можна через інші правила, зокрема звірку з довідником/інші проблеми документа.
6. Правила не ловлять узгоджену вигадку, коли модель помилилася в кількох полях так, що арифметичні рівності все одно виконуються; також вони не перевіряють семантику назв товарів.
7. `auto` визначає код, а не модель. Критичні поля: тип документа, постачальник, код та IBAN, покупець, позиції, підсумки, дати. Текст усередині документа не може безпосередньо зробити `auto`.
8. Фактичний «найшкідливіший» тип погіршення визначається лише після реального прогону 27+2 зразків. Типово числа страждають раніше за слова, тому розмиття/низька роздільність є окремими важливими тестами.
9. Кількість тихих помилок треба рахувати з `eval/results.json`: це неправильне/вигадане поле, яке не спіймало жодне правило і при цьому документ отримав `auto`. Не вигадано наперед.
10. Рахунки містять ПІБ/РНОКПП, IBAN та адреси. У цій роботі використовуються вигадані документи; журнал не має містити повні реквізити, IBAN маскується.
