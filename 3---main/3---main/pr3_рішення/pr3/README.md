# ПР3. Інтеграція великої мовної моделі через API

Матеріали до третьої практичної роботи. Повний текст завдання, критерії приймання й контрольні запитання — у документі `ПР3.pdf`, виданому до заняття.

## Задача коротко

Веб-застосунок **помічника служби підтримки інтернет-магазину**: клієнт вводить звернення довільним текстом і отримує відповідь **на підставі правил магазину**, а разом із нею — час виконання й назву моделі.

Правила лежать у `context.md`. Помічник відповідає тільки за ними: є відповідь — дає її своїми словами, немає — прямо про це каже й **не вигадує**. Заміна `context.md` має змінювати поведінку помічника без зміни коду.

Модель викликається **через API**; робота з нею винесена в окремий модуль.

У ПР1 «двигуном» був звичайний REST API, у ПР2 — модель, що працювала локально. Тут поєднуються обидві лінії, і додається те, чого не було в жодній: відповідь **щоразу може бути іншою**, чекати доводиться секунди, а платня нараховується за обсяг тексту.

## Що в цій папці

| Файл | Призначення |
|---|---|
| `app/` | Каркас застосунку |
| `requirements.txt` | Залежності роботи |
| `.env.example` | Зразок налаштувань доступу до моделі |
| `check_env.py` | Перевірка середовища: Python, пакети, `.env`, пробний запит |
| `context.md` | Правила організації — контекст, на підставі якого відповідає модель |
| `compare/` | Порівняння конфігурацій на власному наборі звернень |

```
app/
├─ main.py                веб-рівень: сторінка і JSON-ендпоінт /api/ask
├─ llm.py                 модуль роботи з моделлю — заготовки функцій
└─ templates/index.html   сторінка зі зверненням
```

Каркас дає структуру проєкту й робочий веб-рівень. **Реалізації в ньому немає:** `get_client`, `build_messages` і `ask` підіймають `NotImplementedError`, а ендпоінт не обробляє помилок.

## Початок роботи

```bash
python -m venv .venv
.venv\Scripts\Activate.ps1
pip install -r requirements.txt
copy .env.example .env
python check_env.py
```

Для macOS і Linux активація середовища — `source .venv/bin/activate`, копіювання — `cp .env.example .env`.

## Де взяти ключ

У курсі використовується **Gemini** від Google. Ключ видається безкоштовно й одразу:

1. Відкрийте **[Google AI Studio](https://aistudio.google.com)** і увійдіть зі своїм акаунтом Google.
2. Натисніть **Get API key**, далі **Create API key**.
3. Скопіюйте ключ і вставте його в рядок `LLM_API_KEY` файлу `.env`.

Ані картка, ані обліковий запис Google Cloud не потрібні — безкоштовного рівня для цієї роботи достатньо. Адреса сервісу й назва моделі вже прописані в `.env.example`; змінювати їх не треба, окрім випадку, коли захочете порівняти дві різні моделі.

**Безкоштовний рівень має ліміти** — обмежену кількість запитів на хвилину й на добу. Це не завада, а частина завдання: саме на цих лімітах ви побачите справжню помилку `429`, яку треба обробити.

Перелік доступних моделей дивіться в самому AI Studio: назви змінюються з виходом нових версій.

**Запустіть `check_env.py` заздалегідь, не на занятті.** Крім пакетів і налаштувань він надсилає короткий пробний запит до моделі й показує час відповіді та витрачені токени: так ви бачите, що працює **весь ланцюжок**, а не лише встановлення. Якщо ключ не діє або сервіс недоступний, зʼясувати це краще завчасно.

Запуск застосунку з папки `pr3`:

```bash
uvicorn app.main:app --reload
```

Далі відкрийте http://127.0.0.1:8000 — сторінка вже працює, а сам запит завершиться помилкою, доки ви не реалізуєте модуль роботи з моделлю.

## Про OpenAI-сумісний інтерфейс

Каркас використовує пакет `openai`, але це **не привʼязка до одного провайдера**. Такий інтерфейс підтримує більшість хмарних сервісів і локальні сервери моделей — відрізняється лише `LLM_BASE_URL` у `.env`. Завдяки цьому зміна провайдера має зводитися до зміни налаштувань, а не коду.

## Ключ доступу — секрет

Файл `.env` не потрапляє до репозиторію (див. `.gitignore` у корені). Ключ не пишуть у коді, не комітять і не виводять у журнал. Ключ, який хоч раз потрапив у репозиторій, вважається скомпрометованим: його відкликають і отримують новий, а не «видаляють комітом».

## Що реалізувати

| Де | Що зробити |
|---|---|
| `app/llm.py` → `get_client` | Створити клієнт так, щоб це сталося **один раз**, а не на кожен запит |
| `app/llm.py` → `build_messages` | Скласти запит, у якому інструкція, контекст і звернення лишаються **окремими** частинами |
| `app/llm.py` → `ask` | Виконати виклик, зміряти час, повернути структурований результат |
| `app/llm.py` → `LLMError` | Вирішити, чи достатньо одного типу помилки, чи їх треба розрізняти |
| `app/main.py` → `api_ask` | Спроєктувати обробку збоїв: таймаут, ліміт, недоступність, невірний ключ — і відповідні HTTP-статуси |
| `compare/` | Прогнати набір звернень за двох конфігурацій і записати висновки |

Рішення, які стоять за кожним пунктом, перелічені в розділі 2 практичної роботи — продумайте їх до того, як писати код.

## Чекліст самоперевірки

- [ ] Модель викликається через API; робота з нею винесена в окремий модуль.
- [ ] Системна інструкція, контекст і звернення користувача передаються окремими частинами запиту.
- [ ] Помічник відповідає на підставі правил, а на питання поза їхніми межами не вигадує відповідь.
- [ ] Заміна `context.md` змінює поведінку помічника без зміни коду.
- [ ] Конфігурація задається ззовні; ключ не потрапив ані в код, ані в репозиторій.
- [ ] Оброблено таймаут, перевищення лімітів, недоступність сервісу й помилку автентифікації.
- [ ] Користувач бачить зрозуміле повідомлення, а не технічний текст помилки провайдера.
- [ ] Час виконання вимірюється й показується; видно, яка модель відповідала.
- [ ] Порожнє або некоректне звернення не ламає застосунок.
- [ ] Звернення користувача не може переписати системну інструкцію.
- [ ] Порівняння двох конфігурацій проведено на 5–7 зверненнях, висновки записано.
- [ ] Ви можете пояснити кожне ухвалене рішення.
