# ПР2 — Локальний inference object detection (YOLO + FastAPI)

## Структура проєкту

```
pr2/
├── requirements.txt
├── check_env.py          # запустити ЗАЗДАЛЕГІДЬ: перевіряє пакети + завантажує ваги моделі
├── app/
│   ├── main.py            # веб-рівень (FastAPI): ендпоінти, статус-коди, HTML-сторінка
│   ├── model.py            # inference-модуль: Detector — уся робота з YOLO тут і тільки тут
│   ├── schemas.py           # Pydantic-схеми відповіді /detect
│   └── static/index.html     # проста сторінка: завантаження файлу, повзунок порогу, canvas з рамками
└── eval/
    ├── README.md            # інструкція для збору прикладів оцінювання
    ├── expected.json         # шаблон очікуваних об'єктів (заповнити самостійно)
    ├── analysis.md            # шаблон таблиці результатів і спостережень
    └── images/                 # сюди покласти 5–7 власних тестових зображень
```

## Встановлення й запуск

```bash
pip install -r requirements.txt
python check_env.py          # одноразово: перевірка + завантаження ваг yolov8n
uvicorn app.main:app --reload
```

Відкрити http://127.0.0.1:8000 — завантажити зображення, за потреби змінити
поріг confidence повзунком, натиснути «Розпізнати».

API напряму (наприклад, curl):

```bash
curl -X POST "http://127.0.0.1:8000/detect?threshold=0.3" \
  -F "file=@eval/images/photo_01.jpg"
```

Відповідь — JSON з полями `objects` (клас, confidence, рамка для кожного
об'єкта), `count`, `inference_time_ms`, розмірами зображення й
використаним порогом.

## Ключові рішення (щоб уміти пояснити)

- **Поріг confidence** — параметр запиту (`?threshold=0.25` за замовчуванням),
  користувач може його змінювати повзунком на сторінці. Це свідомо: «правильного»
  порога немає, він залежить від задачі, тож рішення винесено назовні коду.

- **Де завантажується модель.** У `app/main.py` — у `lifespan`-хендлері
  FastAPI, який виконується рівно один раз при старті процесу. `Detector`
  зберігається в модульній змінній і перевикористовується для всіх
  наступних запитів. У конструкторі `Detector` додатково виконується
  «прогрів» моделі на фейковому зображенні, щоб час *першого* реального
  запиту користувача не був спотворений одноразовими витратами ініціалізації.

- **Межа inference / решта застосунку.** `app/model.py` не імпортує нічого
  з FastAPI і не знає про HTTP: на вхід — байти зображення й поріг, на
  вихід — прості dataclass-и (`Detection`, `DetectionResult`). Веб-рівень
  (`app/main.py`) відповідає лише за приймання файлу, валідацію,
  перетворення виключень на HTTP-статуси та серіалізацію в Pydantic-схему.
  Така межа дозволяє, наприклад, покрити `model.py` unit-тестами без
  підняття веб-сервера, або підключити інший веб-фреймворк без зміни логіки inference.

- **Вимірювання часу.** Таймер (`time.perf_counter`) охоплює лише виклик
  `model.predict(...)` — без читання файлу, декодування зображення чи
  серіалізації JSON. На цей час впливають: розмір вхідного зображення,
  апаратне забезпечення (CPU/GPU), розмір моделі (тут — yolov8n, найлегша
  вага) та стан «прогріву» (перший виклик завжди повільніший, тому прогрів
  винесено в конструктор).

- **Обробка некоректного вводу.** `Detector.detect` кидає власний виняток
  `InvalidImageError` для порожніх файлів і файлів, які PIL не може
  розпізнати як зображення (биті дані, невідповідний формат). `app/main.py`
  перетворює це на `HTTP 400`. Файл, чий `Content-Type` не починається з
  `image/`, відхиляється ще раніше (теж `400`). Занадто великий файл (>15 МБ)
  повертає `413`. Якщо модель з якоїсь причини не готова — `503`.

## Контрольні запитання
