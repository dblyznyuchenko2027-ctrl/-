# ПР9. Побудова багатоетапного AI workflow

Матеріали до девʼятої практичної роботи. Повний текст завдання, критерії приймання й контрольні запитання — у документі `ПР9.pdf`, виданому до заняття.

## Задача коротко

У ПР8 помічник сам вирішував, які інструменти викликати й у якому порядку. Звернення «хочу повернути пилосос із замовлення 10412» щодня обробляється тими самими кроками: зрозуміти, про що просять, знайти замовлення, перевірити правила, оформити заявку, відповісти. Тепер послідовність задає **ваш код**, а модель виконує лише ті кроки, де потрібне розуміння мови: розбір звернення й відповідь клієнтові.

Заявка на повернення чи скасування змінює дані, тому workflow **зупиняється перед нею**, доки оператор не підтвердить. Пауза може тривати годину, а застосунок за цей час можуть перезапустити, тож стан звернення **зберігається на диску**. Кожне звернення має обмеження — кроки, час, токени — і доходить до кінцевого стану.

Наприкінці — той самий набір звернень обробляється **агентом із ПР8**, і два підходи порівнюються.

## Що в цій папці

| Файл | Призначення |
|---|---|
| `app/` | Каркас застосунку |
| `shop/` | Сервіс магазину — той самий, що в ПР8, **готовий**, змінювати не потрібно |
| `requirements.txt` | Залежності роботи |
| `.env.example` | Зразок налаштувань: доступ до моделі, обмеження агента й workflow, каталог стану, поведінка сервісу магазину |
| `check_env.py` | Перевірка середовища: Python, пакети, `.env`, сервіс магазину, перенесені модулі ПР8, каталог стану, пробний structured output |
| `eval/` | Порівняння workflow й агента на наборі звернень |

```
app/
├─ main.py                веб-рівень: сторінка, /api/requests, /api/runs, /api/runs/{id}/decision
├─ workflow.py            кроки, переходи, обмеження — заготовка
├─ state.py               стан звернення: Run, Step
├─ store.py               збереження стану на диску — заготовка
├─ schema.py              схема розбору звернення — заготовка
├─ tools.py               ┐
├─ llm.py                 │ замініть своїми файлами з pr8/app/
├─ assistant.py           ┘ (у llm.py допишіть виклик без інструментів)
└─ templates/index.html   сторінка: звернення, журнал кроків, черга оператора

shop/
├─ service.py             функції сервісу
└─ data/                  клієнти, замовлення, товари, склад, тарифи доставки
```

Каркас дає структуру проєкту й робочий веб-рівень. Сторінка дає обрати клієнта (це заміняє вхід у кабінет), надіслати звернення на обробку workflow або агентом, показує стан звернення з журналом кроків і використанням обмежень, чергу оператора з кнопками «підтвердити» й «відхилити» і перелік усіх звернень. **Реалізації в каркасі немає:** функції в `app/` підіймають `NotImplementedError`, ендпоінти не обробляють збоїв.

## Початок роботи

1. **Середовище:**

   ```bash
   python -m venv .venv
   .venv\Scripts\Activate.ps1
   pip install -r requirements.txt
   copy .env.example .env
   ```

   Для macOS і Linux активація середовища — `source .venv/bin/activate`, копіювання — `cp .env.example .env`. Ключ доступу перенесіть у `.env` з папки попередньої роботи.

2. **Модулі з ПР8** — скопіюйте свої `tools.py`, `llm.py`, `assistant.py` з `pr8/app/` поверх заготовок у `app/`. Перш ніж замінювати `llm.py`, перенесіть із заготовки до свого файлу функцію `complete` — виклик моделі без інструментів, потрібний workflow. Якщо в ПР8 ви змінювали `answer_to_dict` у `main.py`, перенесіть і її.

3. **Перевірка:**

   ```bash
   python check_env.py
   ```

   Запустіть заздалегідь. Скрипт покаже, чи перенесено модулі ПР8, чи доступний для запису каталог стану і чи приймає провайдер схему для structured output: модель розбирає коротке звернення без номера замовлення, і видно, що вона ставить у поле, якого клієнт не називав.

Запуск застосунку з папки `pr9`:

```bash
uvicorn app.main:app --reload
```

Далі відкрийте http://127.0.0.1:8000 — сторінка вже працює й показує клієнтів, а обробка звернення завершиться помилкою, доки ви не реалізуєте модулі.

## Що очікує сторінка

Нове звернення — `POST /api/requests` з `{"customer_id": "C-1003", "text": "...", "mode": "workflow"}`. Для `workflow` у відповідь сторінка очікує стан звернення — `Run` з `app/state.py`, перетворений функцією `run_to_dict`: `run_id`, `status`, `route`, `steps`, `pending`, `decision`, `reply`, `stopped`, `usage`, `elapsed` і `limits`. Кожен елемент `steps` — `Step`: `{"n": 1, "name": "parse", "kind": "model", "status": "ok", "detail": "...", "input": ..., "output": ..., "elapsed": 0.9, "usage": {...}}`. Типи `model`, `tool`, `code`, `human` і відомі статуси сторінка позначає кольором, інші показує як є. Для `agent` — те саме, що в ПР8 (`answer_to_dict`).

Черга оператора — `GET /api/runs?status=awaiting_approval`; якщо ваш статус очікування називається інакше, змініть константу `WAITING_STATUS` на сторінці. Для дії, що чекає підтвердження, сторінка показує поля `pending.summary`, `pending.tool`, `pending.arguments`, `pending.grounds`, якщо вони є, і решту як є. Рішення оператора — `POST /api/runs/{run_id}/decision` з `{"approve": true, "comment": "..."}`.

## Що реалізувати

| Де | Що зробити |
|---|---|
| `app/tools.py`, `app/llm.py`, `app/assistant.py` | Перенести з ПР8; у `llm.py` — виклик без інструментів зі structured output і без нього |
| `app/schema.py` → `request_schema`, `validate` | Схема розбору звернення і перевірка відповіді моделі за нею |
| `app/workflow.py` → `start`, `resume` | Кроки й переходи; дані між кроками; інструменти кожного кроку; пауза на підтвердження і продовження; виконання дії рівно один раз; обмеження кроків, часу й токенів; відповідь клієнтові та її перевірка; журнал кроків |
| `app/state.py` | За потреби — доповнити склад стану |
| `app/store.py` → `save`, `load`, `list_runs` | Збереження стану поза памʼяттю процесу, атомарний запис |
| `app/main.py` | Обробити збої: порожній текст, невідомий клієнт, невідоме звернення, рішення щодо звернення, яке не чекає підтвердження, збої моделі й сервісу |
| `eval/` | Порівняння з агентом, окремі перевірки, висновки |

Рішення, які стоять за кожним пунктом, перелічені в розділі 2 практичної роботи — продумайте їх до того, як писати код.

## Чекліст самоперевірки

- [ ] Workflow обробляє повернення, скасування і питання про стан замовлення; решта й незрозумілі звернення — уточнення або передача оператору.
- [ ] Послідовність задає код; модель — лише на кроках, де потрібне розуміння мови; її вихід перевіряється схемою й змістом.
- [ ] Дані магазину — інструментами з ПР8; клієнт — із сеансу; чуже замовлення не прочитати й не змінити.
- [ ] Кожному кроку доступні лише його інструменти; дія зі змінами — тільки після підтвердження, і це забезпечує код.
- [ ] Подвійне підтвердження, повторне звернення й перезапуск не створюють другої заявки; перед виконанням умови перевіряються ще раз.
- [ ] Оператор бачить дію з аргументами й підстави; відхилення завершується відповіддю клієнтові.
- [ ] Стан зберігається на диску; звернення, що чекає підтвердження, переживає перезапуск; статус змінюється лише дозволеними переходами.
- [ ] Кожне звернення доходить до кінцевого стану; кроки, час і токени обмежено конфігурацією; причину зупинки видно на сторінці.
- [ ] Відповідь клієнтові — за фактами зі стану й перевіряється кодом; службових даних у ній немає.
- [ ] Текст звернення, адресований «системі», не змінює ходу обробки.
- [ ] Застосунок не падає: збій моделі, недоступний сервіс, невалідний розбір дають контрольований стан, а не 500.
- [ ] Межі модулів: модель — без магазину, інструменти — без API моделі, сховище — без моделі й магазину, веб-рівень — лише через workflow.
- [ ] Ключ не потрапив ані в код, ані в репозиторій; каталог стану — теж.
- [ ] Набір і щонайменше три власні звернення прогнано workflow й агентом по три рази; перезапуск, повтор, межі й відмови сервісу перевірено; висновки записано.
- [ ] Ви можете пояснити кожне ухвалене рішення.
