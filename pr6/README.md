# ПР6. RAG-помічник за власною базою знань

Матеріали до шостої практичної роботи. Повний текст завдання, критерії приймання й контрольні запитання — у документі `ПР6.pdf`, виданому до заняття.

## Задача коротко

У ПР5 пошук повертав фрагменти документів, і читав їх користувач. Тут їх читає **мовна модель**: за питанням клієнта помічник знаходить кілька фрагментів бази знань магазину «Сузірʼя», віддає їх моделі разом із інструкцією й повертає відповідь **із джерелами**, на які вона спирається. Якщо відповіді в базі немає — помічник прямо про це каже, а не вигадує. Це і є retrieval-augmented generation: пошук з ПР5 плюс модель із ПР3–ПР4, зʼєднані шаром, який вирішує, що модель побачить і чому можна вірити в тому, що вона повернула.

Наприкінці — перевірка на наборі питань із відомими відповідями й розбір помилок на два кошики: помилки пошуку і помилки генерації.

## Що в цій папці

| Файл | Призначення |
|---|---|
| `app/` | Каркас застосунку |
| `docs/` | Та сама колекція документів, що в ПР5; опис — у `docs/README.md` |
| `ingest.py` | Побудова індексу — той самий, що в ПР5 |
| `requirements.txt` | Залежності роботи: ПР4 + ПР5 разом |
| `.env.example` | Зразок налаштувань: доступ до моделі, ембедінги, збирання контексту |
| `check_env.py` | Перевірка середовища: Python, пакети, `.env`, колекція, модель ембедінгів, пробний запит до мовної моделі |
| `eval/` | Перевірка помічника на наборі питань і класифікація помилок |

```
app/
├─ main.py                веб-рівень: сторінка, /api/status, /api/ask
├─ documents.py           ┐
├─ embeddings.py          │ модулі пошуку з ПР5 — заготовки;
├─ index.py               │ замініть своїми файлами з pr5/app/
├─ keyword.py             ┘
├─ retrieval.py           відбір фрагментів для моделі й збирання контексту — заготовки
├─ llm.py                 модуль роботи з моделлю — заготовки
├─ schema.py              контракт відповіді моделі — заготовка
├─ rag.py                 конвеєр: знайти → зібрати → спитати → перевірити — заготовка
└─ templates/index.html   сторінка: питання, відповідь, джерела, «що бачила модель»
```

Каркас дає структуру проєкту й робочий веб-рівень: сторінка надсилає питання, показує відповідь із позначкою «за базою знань / у базі немає», перелік джерел, службові дані та — окремим блоком — фрагменти, які бачила модель. **Реалізації в ньому немає:** усі функції нових модулів підіймають `NotImplementedError`, ендпоінт не обробляє збоїв, а модулі пошуку лишені заготовками з ПР5 — їх ви замінюєте своїми.

## Початок роботи

```bash
python -m venv .venv
.venv\Scripts\Activate.ps1
pip install -r requirements.txt
copy .env.example .env
python check_env.py
```

Для macOS і Linux активація середовища — `source .venv/bin/activate`, копіювання — `cp .env.example .env`.

Далі три перенесення з попередніх робіт:

1. **Ключ доступу** — у `.env` перенесіть `LLM_API_KEY` із `.env` папки `pr4` (або `pr3`). Файл `.env` потрібен у кожній папці окремо й до репозиторію не потрапляє.
2. **Модулі пошуку** — скопіюйте свої `documents.py`, `embeddings.py`, `index.py`, `keyword.py` з `pr5/app/` поверх заготовок у `app/`. Якщо в ПР5 ви змінювали налаштування ембедінгів чи поділу — перенесіть їх у `.env`.
3. **Індекс** — збудуйте його тут заново: `python ingest.py`. Індекс до репозиторію не потрапляє.

**Запустіть `check_env.py` заздалегідь.** Він завантажує модель ембедінгів (уже в кеші після ПР5) і надсилає пробний запит до мовної моделі з одним реченням контексту — покаже, чи працює ключ і скільки триває відповідь.

Запуск застосунку з папки `pr6`:

```bash
uvicorn app.main:app --reload
```

Далі відкрийте http://127.0.0.1:8000 — сторінка вже працює, а сам запит завершиться помилкою, доки ви не реалізуєте модулі.

## Що очікує сторінка

При відкритті сторінка викликає `GET /api/status` і показує, чи збудовано індекс. Питання — `POST /api/ask` з обʼєктом `{"question": "...", "filters": {"product": "Вега S"}}`; фільтри можуть бути порожніми.

У відповідь сторінка очікує `{"answer": "...", "found": true, "sources": [...], "retrieved": [...], "model": "...", "elapsed": {"retrieval": 0.04, "generation": 1.9}, "usage": {...}}`. Кожне джерело — `{"ref": 1, "score": 0.83, "source": "файл.md", "metadata": {...}, "text": "..."}`; `retrieved` — фрагменти в тому вигляді, у якому їх бачила модель. Веб-рівень збирає цей обʼєкт з `rag.Answer` функцією `answer_to_dict` — якщо зміните склад `Answer`, змініть і її, і сторінку; вони ваші.

## Що реалізувати

| Де | Що зробити |
|---|---|
| `app/documents.py`, `embeddings.py`, `index.py`, `keyword.py` | Замінити заготовки своєю реалізацією з ПР5 |
| `app/retrieval.py` → `retrieve` | Відібрати фрагменти для моделі: яким пошуком, з якими обовʼязковими фільтрами, скільки, з яким порогом |
| `app/retrieval.py` → `build_context` | Зібрати контекст: порядок, позначки джерел, бюджет |
| `app/schema.py` → `output_schema`, `validate` | Контракт відповіді моделі: текст, посилання на джерела, чи знайдено відповідь |
| `app/llm.py` → `get_client`, `build_messages`, `ask` | Інструкція для відповіді за документами, збирання запиту, виклик, перевірка, збої |
| `app/rag.py` → `answer` | Конвеєр: що робити з порожнім пошуком, як перевірити посилання й поле «знайдено», що показати як джерела |
| `app/main.py` → `api_ask` | Обробити збої: порожнє питання, відсутній індекс, невідомий фільтр, збої моделі, невалідна відповідь |
| `eval/` | Набір питань, прогін, класифікація помилок на пошук і генерацію, одна зміна, висновки |

Рішення, які стоять за кожним пунктом, перелічені в розділі 2 практичної роботи — продумайте їх до того, як писати код.

## Чекліст самоперевірки

- [ ] На питання з відповіддю в базі помічник відповідає за документами й посилається на джерела, які справді містять сказане.
- [ ] На питання без відповіді в базі помічник прямо каже, що інформації немає, і не вигадує.
- [ ] Внутрішні документи не потрапляють до моделі, коли питає клієнт, — і це забезпечує код, а не користувач.
- [ ] Контекст збирається з обмеженої кількості фрагментів у межах бюджету; кожен фрагмент позначено джерелом.
- [ ] Відповідь моделі перевіряється за схемою; посилання на джерела перевіряються кодом.
- [ ] Сторінка показує відповідь, позначку «знайдено / немає», джерела, фрагменти, які бачила модель, час пошуку й генерації, токени.
- [ ] Застосунок не падає: без індексу каже, що робити; порожнє питання, збій моделі, невалідна відповідь дають зрозумілу помилку.
- [ ] Модуль пошуку не знає про модель, модуль моделі — про індекс, веб-рівень — ні про що з цього.
- [ ] Ключ не потрапив ані в код, ані в репозиторій.
- [ ] Перевірку проведено на 12–15 питаннях; помилки поділено на помилки пошуку й помилки генерації; одну зміну перевірено окремо; висновки записано.
- [ ] Ви можете пояснити кожне ухвалене рішення.
