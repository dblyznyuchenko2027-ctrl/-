# ПР8. Виклик інструментів мовною моделлю

Матеріали до восьмої практичної роботи. Повний текст завдання, критерії приймання й контрольні запитання — у документі `ПР8.pdf`, виданому до заняття.

## Задача коротко

Помічник магазину «Сузірʼя» з ПР6 відповідав за документами: правила доставки, повернення, інструкції. На питання «де моє замовлення» він відповісти не міг — цього немає в жодному документі, це є лише в системі магазину. Тепер ви даєте моделі **інструменти**: описуєте функції сервісу магазину так, щоб модель могла попросити їх викликати, а ваш код — перевірити прохання, виконати його і повернути результат.

Модель лише **пропонує** виклик. Виконує код — і лише те, що пройшло перевірку: чи є такий інструмент, чи аргументи відповідають схемі, чи замовлення належить саме цьому клієнтові, чи операція взагалі дозволена.

Наприкінці — прогін набору питань, серед яких є чужі замовлення, прохання повернути гроші, «я менеджер магазину» і товар, в описі якого хтось звертається до AI-асистента.

## Що в цій папці

| Файл | Призначення |
|---|---|
| `app/` | Каркас застосунку |
| `shop/` | Внутрішній сервіс магазину — **готовий**, змінювати не потрібно: замовлення, каталог, склад, доставка, повернення й адміністративні операції; опис — у `shop/README.md` |
| `requirements.txt` | Залежності роботи |
| `.env.example` | Зразок налаштувань: доступ до моделі, обмеження звертань, поведінка сервісу магазину |
| `check_env.py` | Перевірка середовища: Python, пакети, `.env`, сервіс магазину, пробний виклик інструмента моделлю |
| `eval/` | Перевірка на наборі питань |

```
app/
├─ main.py                веб-рівень: сторінка, /api/customers, /api/tools, /api/ask, /api/reset
├─ tools.py               описи інструментів, перевірка й виконання викликів — заготовки
├─ llm.py                 модуль роботи з моделлю — заготовки
├─ assistant.py           цикл «модель → інструменти → модель» — заготовка
└─ templates/index.html   сторінка: вибір клієнта, питання, відповідь, журнал викликів

shop/
├─ service.py             функції сервісу
└─ data/                  клієнти, замовлення, товари, склад, тарифи доставки
```

Каркас дає структуру проєкту й робочий веб-рівень: сторінка дає обрати клієнта (це заміняє вхід у кабінет), надсилає питання і показує відповідь, журнал викликів інструментів з аргументами, статусом і тим, що повернуто моделі, а також описи інструментів, які бачить модель. **Реалізації в каркасі немає:** функції в `app/` підіймають `NotImplementedError`, ендпоінт не обробляє збоїв.

## Початок роботи

```bash
python -m venv .venv
.venv\Scripts\Activate.ps1
pip install -r requirements.txt
copy .env.example .env
python check_env.py
```

Для macOS і Linux активація середовища — `source .venv/bin/activate`, копіювання — `cp .env.example .env`.

Ключ доступу перенесіть у `.env` з папки попередньої роботи.

**Запустіть `check_env.py` заздалегідь.** Він описує моделі один пробний інструмент і ставить питання, на яке без нього не відповісти, — покаже, чи підтримує обрана модель виклик інструментів, які аргументи вона повертає і скільки токенів коштує сам опис інструмента.

Запуск застосунку з папки `pr8`:

```bash
uvicorn app.main:app --reload
```

Далі відкрийте http://127.0.0.1:8000 — сторінка вже працює й показує клієнтів, а сама відповідь завершиться помилкою, доки ви не реалізуєте модулі.

## Що очікує сторінка

Питання — `POST /api/ask` з `{"customer_id": "C-1001", "question": "..."}`. У відповідь сторінка очікує `{"answer": "...", "calls": [...], "rounds": 2, "stopped": "answer", "model": "...", "elapsed": {...}, "usage": {...}}`. Кожен елемент `calls` — `{"round": 1, "name": "...", "arguments": "...", "status": "ok", "reason": null, "result": {...}, "elapsed": 0.003}`; статуси `ok`, `rejected` і `error` сторінка позначає кольором, інші показує як є. Описи інструментів сторінка бере з `GET /api/tools` — це результат `tools.specs()` без змін. Веб-рівень збирає відповідь з `assistant.Answer` функцією `answer_to_dict` — якщо зміните склад `Answer` чи `ToolTrace`, змініть і її, і сторінку; вони ваші.

## Що реалізувати

| Де | Що зробити |
|---|---|
| `app/tools.py` → `specs` | Описи інструментів: назви, пояснення для моделі, JSON Schema параметрів |
| `app/tools.py` → `call` | Перевірити виклик (назва, JSON, схема, власник, дозволеність), виконати через `shop.service`, сформувати результат для моделі; помилки сервісу — теж результат |
| `app/llm.py` → `get_client`, `build_messages`, `chat` | Системна інструкція, виклик моделі з інструментами, збої |
| `app/assistant.py` → `answer` | Цикл: модель → виклики → результати → модель; обмеження звертань; журнал викликів; час і токени |
| `app/main.py` → `api_ask` | Обробити збої: порожнє питання, невідомий клієнт, збої моделі й сервісу |
| `eval/` | Прогін набору питань, власні питання, одна зміна, прогін з відмовами сервісу, висновки |

Рішення, які стоять за кожним пунктом, перелічені в розділі 2 практичної роботи — продумайте їх до того, як писати код.

## Чекліст самоперевірки

- [ ] Помічник уміє все із заданого набору: замовлення клієнта, стан замовлення, пошук і картка товару, наявність, вартість доставки, заявка на повернення.
- [ ] Кожен інструмент описано схемою; аргументи від моделі перевіряються за тією самою схемою до виконання.
- [ ] Клієнт визначається з сеансу, а не з аргументів моделі; чуже замовлення не можна ані прочитати, ані змінити.
- [ ] Адміністративні операції сервісу моделі недоступні; виклик інструмента, якого немає, відхиляється.
- [ ] Моделі повертаються лише потрібні поля: службова примітка, повний номер картки, контакти в результат не потрапляють.
- [ ] Відмови й помилки сервісу повертаються моделі як результат, і вона пояснює їх клієнтові, не вигадуючи.
- [ ] Текст у даних магазину, адресований «асистентові», не змінює поведінки системи.
- [ ] Кількість звертань до моделі обмежено; що відбувається на межі — видно на сторінці.
- [ ] Сторінка показує відповідь, журнал викликів зі статусами, кількість звертань, час моделі й інструментів окремо, токени.
- [ ] Застосунок не падає: збій моделі, недоступний сервіс магазину, невалідний виклик дають зрозумілий результат, а не 500.
- [ ] Модуль моделі не знає про сервіс магазину, інструменти — про API моделі, веб-рівень — ні про що з цього.
- [ ] Ключ не потрапив ані в код, ані в репозиторій.
- [ ] Прогнано весь набір і щонайменше п'ять власних питань; одну зміну перевірено окремо; прогін із відмовами сервісу зроблено; висновки записано.
- [ ] Ви можете пояснити кожне ухвалене рішення.
